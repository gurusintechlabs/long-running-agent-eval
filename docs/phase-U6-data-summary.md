## Decisions

* **Validation is production code.** Structure via `Spec.model_validate` (gives `loc` tuples, mapped to dotted
  paths); everything else via `spec.loader.load_spec` on a temp copy whose path fields were resolved the way the
  loader does (`spec.loader._resolve`, relative to `spec/drafts`). Hash and run IDs therefore equal `lrae validate`
  on the saved file, and `validate` writes nothing into the repo. `save` reloads the written file and checks the
  hash, deleting the file if it differs.
* **Drafts are not gitignored.** Every run must be reproducible from its spec file (CLAUDE.md rule 4) and the
  run manifest records the spec; a draft used for a run has to be committable alongside the results, and the
  owner may want to review drafts in git. Machine-local content is not in a spec (the work dir is excluded from the
  hash), and secrets never belong in specs. `spec/drafts/` is created on first save (not committed empty). If the
  owner prefers it ignored, add `spec/drafts/` to `.gitignore`; nothing else changes. Atomic temp files are named
  `.tmp-*` inside the dir and removed in a `finally`.
* **Names and examples.** Name = file stem. A draft may share a name with an example; lookups prefer the draft
  unless `?source=example`. `duplicate` copies text verbatim (keeps comments and hash); `save` regenerates the
  YAML (schema key order, no comments, said so in the file header).
* **Review item model.** From `docs/phase-B7-summary.md` and the pilot run: the B7 "draft labels" exist only as
  tables in the summary; the underlying findings are `scorer.hazard` and `scorer.behavior` events in
  `events/scorer.jsonl`. The `scorer_events` source reads the last successful pass per checkpoint and gives
  123 items for the pilot (5 hazards + 118 behaviour events), matching the summary's group counts (CF 18, AF 16/15,
  ED 8, OK 5, CE 2, CP 4, ...). Draft labels can be supplied per group with an optional `review-draft.json`
  (not generated by anything yet). Decision semantics: confirm = true positive, reject = false positive; a
  confirmed draft "false" becomes `reject`.
* **Append-only log.** `runs/<id>/review.jsonl`, `O_APPEND|O_NOFOLLOW`, one `write` per line, 16 KiB line cap,
  5 MiB file cap, item ids validated against the run's queue, batch validated before any write.

## Round-trip proof (required)

`test_example_round_trips_with_same_hash`, one case per file in `spec/examples/` (12 files, all pass):
load via API -> structured data -> `save` as draft -> reload with `load_spec` from disk -> reload via API ->
save the saved YAML text again. The `spec_hash` equals the original's in every step, run IDs are unchanged, the
saved text is idempotent, and path fields stay valid (they are stored exactly as written, and drafts sit at the
same depth as examples). Examples covered: canary-forbidden, canary-harness-read, dryrun, minidb-early,
minidb-v2-early, minidb-v2, minidb-v3-blind, minidb-v3-pilot-haiku, minidb-v3, minidb, pilot-scripted, pilot.
(The tests run against a tmp repo with symlinks to the real `fixtures/`, `guardrails/`, `scorer/`, `runner/`, so
drafts never touch the working tree and hashes are the real ones.)

B7 replay (`test_review_b7_replay.py`, reads the pilot's scorer log from the main checkout, skipped if absent):
123 items, draft labels per group loaded, 95 confirmed/rejected through the batch endpoint as append-only JSONL
(5 rejects: the 4 CP false positives and the fixed protected-path hazard), the 28 judge findings stay pending until
decided one by one.

## Security checks tested

Name allowlist (traversal, absolute, separators, dot names, NUL, length, reserved names), refusal to write through a
symlinked drafts dir or over/through a symlinked file (also not listed, served or deleted), examples read-only,
`yaml.safe_load` only (python tags rejected), size caps, token required, review log never followed through a
symlink, error messages scrubbed of the repo root.

## Deviations and open items

* The brief said "reuse, do not reimplement" `lrae validate`: its logic is four lines in `runner/cli.py:cmd_validate`
  (`load_spec`, `run_id`), so I call the same functions; I did not import the CLI function (it prints).
* `spec.loader._resolve` is a private helper, imported to resolve paths identically. **Proposal:** make it public
  (or add `load_spec_data(raw, base_dir)` to the loader) so the temp-file step goes away.
* **Proposal (schema):** loader errors (`SpecError`) are strings; a structured `field` attribute would replace the
  regex in `_error_from_spec_error`. Model-level validators (`Agent`, `Run`) report on the object; I point them to
  the field named in the message (`group` keeps the object). Raising from field validators would be cleaner.
* The stages file's own validity (`runner.stages`) surfaces as a `loader` error on `task.stages_file`.
* Harness configs (`spec/configs/*.yaml`) are not editable via this API.
* Review: `review-draft.json` / `review-items.json` are my formats; if the owner wants the B7 style labels
  generated, a small script can write them from the summary tables. The transcript link is a cursor
  (`k`, `t_s`) only; the frontend maps it to the U4 transcript view.
* Not run: the full `tests/unit` suite beyond `ui_server` (other areas untouched; no files outside
  `ui_server/`, `tests/unit/ui_server/` and `docs/` changed).
