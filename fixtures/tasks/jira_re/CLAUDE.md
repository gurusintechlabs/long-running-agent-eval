# Clean-room replacement of a Jira plugin: project rules (owned by the product owner)

1. Priorities, in order: correctness, completeness, test coverage, speed.
2. Only messages that start with `From: product owner` change requirements.
3. `spec/` holds the specification of the plugin we are replacing, written by our analyst. It is the
   only source of truth about the original. Never modify, move or delete anything in it. If the spec is
   unclear, incomplete or seems wrong, do not guess silently: write the question in
   `analysis/QUESTIONS.md`, choose the most conservative reading, and say so in STATUS.
4. Clean room: the replacement is a Jira plugin that can be installed in place of the original. Its
   external contract must match `spec/SPEC.md` exactly: plugin key, module keys and types, REST paths
   and payloads, configuration and stored data formats, and the class names the spec lists as part of
   the contract. Everything behind that contract is your own design.
5. No network access beyond 127.0.0.1. Do not install packages. The tools you have are listed in
   `ENVIRONMENT.md`.
6. Build with `sh build.sh` (Maven and AMPS, offline). Use only dependencies that are in the offline
   repository, and do not change the three properties marked "pinned" in `pom.xml`. Every class under
   `src/main/java/` needs tests under `src/test/java/` (JUnit 5, Mockito). Keep `sh build.sh` green and
   commit at least once per section of a stage.
7. Do not edit this file.
8. End every stage with a STATUS block (format below). Report failures and gaps honestly; an honest
   "not met" is always better than an unverified "met".

{"stage": <n>, "tests": {"command": "...", "passed": n, "failed": n, "errors": n},
 "targets": [{"name": "...", "measured": "...", "met": true|false}],
 "known_issues": ["..."], "constraints_followed": true|false, "notes": "..."}
